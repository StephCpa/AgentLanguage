# AL-0 实验与实施计划

实验必须分别回答协议正确性、语言表达能力和开发收益。所有基线使用共同任务、同样权限与预算政策，禁止把“不支持此功能”与“实现出现违规”混为同一个失败类别。

## 研究问题与预设判据

| 问题 | 主要证据 | 能否支持贡献 |
| --- | --- | --- |
| RQ1 规则组合后是否保持安全 | 形式证明、模型反例、故障注入 | 支持协议与语言语义主张 |
| RQ2 独立语言是否减少开发错误 | 同运行时 SDK 的配对开发任务 | 支持独立语言价值 |
| RQ3 额外约束是否损害任务效用 | 正常任务完成、误拒、成本和延迟 | 确定可用范围 |
| RQ4 模型能否有效生成和修复程序 | 固定模型的首次通过率、最终正确率及修复费用 | 支持面向模型生成的设计 |
| RQ5 哪个机制带来收益 | 类型、诊断、运行时和身份机制消融 | 避免错误归因 |

安全门槛：任一范围内可复现的越权、审批替换或许可双花阻断发布。效用门槛可预设正常完成率相对强基线的不劣界限为 5 个百分点，以配对差异区间判断。5 个百分点是待预注册的产品容忍度，不是既有实验结论。

语言投入门槛：若 AL-0 对同运行时 SDK 没有可辨认的严重错误或维护成本收益，则优先发布运行时、IR 与 SDK；不把语法本身视为必须保留的产品。

## 分层基线

| 组别 | 前端 | 静态检查 | 运行时 |
| --- | --- | --- | --- |
| A | AL-0 | 全部类型、效应与资源规则 | 共同网关及账本 |
| B | Python SDK | 成熟类型工具及 SDK 合法约束 | 与 A 完全相同 |
| C | AL-0 | 去掉选定静态规则，以运行时检查承接 | 与 A 完全相同 |
| D | Python SDK | 与 B 相同 | 合理配置的持久框架与适配器 |
| E | 现有语言或协议实现 | 按官方支持方式使用 | 对齐共同任务子集 |

A 对 B 估计语言整体收益；A 对 C 估计静态规则收益；B 对 D 估计运行时收益。E 包含 ETAS、LBAC、Quasar 与相关守恒协议适用的实验轨道；分别报告接入工作量和不适用任务，不给统一虚假排名。

SDK 不能被刻意削弱。允许它使用泛型、私有构造函数、代码生成、成熟静态检查和相同诊断内容。对模型生成实验，文档长度、样例数量、工具描述和可用修复预算应尽可能匹配；另报告相同 token 预算与相同任务说明下的敏感性分析。

当前 SDK 的公共构造接口已有固定 mypy 严格验收、结果类型传播和可复现正反例，见 [SDK 静态类型验收](25-sdk-static-typing.md)。固定 Catalog 快照的 schema/工具接口生成、字段来源保持和目录漂移拒绝也已接通，见 [Catalog 类型绑定](26-catalog-type-bindings.md)。实验中的 B 组应使用生成绑定，并同时通过类型工具、SDK 构造和共享 IR 检查；不得跳过后两层，再把本可被共享检查器拒绝的许可复用等错误算作 AL-0 独有收益。运行时变化的 schema 类型精化及真实开发任务对照尚未验收。

## 三类工作负载

### 文献研究与报告

程序搜索材料、生成摘要、检查引用对应关系、输出报告。模拟工具返回诱导扩权、秘密上下文、过期来源和伪造完成声明。任务成功要求内容满足明确可检查的题目和引用条件；事实质量另经人工或可重复规则评估，不能把类型通过当摘要真实。

### 代码修复与提交

从固定仓库快照生成补丁、执行测试、准备合并并经条件写入提交。故障包括证据与补丁替换、测试后基线变化、审批后参数变化、提交成功但响应丢失，以及恢复到旧检查点。

实际 evaluator 检查仓库状态和测试执行的 artifact，不能仅查看 Agent 说“测试通过”。避免只有单一显而易见错误的任务；包含跨模块修改、依赖变化和有多个合理补丁的任务。

### 多步骤业务工单

包含订单更新、库存、通知和模型问答；允许用户或另一个执行者改变共享环境。借鉴 [τ-bench](https://arxiv.org/abs/2406.12045) 的终态评价及重复可靠性，并使用 [τ²-bench](https://arxiv.org/abs/2506.07982) 的双控制场景思想。跨端点任务的判据必须区分部分成功和未决项。

注入攻击轨道使用 [AgentDojo](https://arxiv.org/abs/2406.13352) 的适用环境，并增加其原任务不覆盖的恢复与计费故障。不要将新增故障结果直接当作原基准排行榜结果。

## 故障矩阵

| 类别 | 注入位置或行为 | 外部 oracle 检查 |
| --- | --- | --- |
| 接纳原子性 | 消费、预留、插入操作和 outbox 之间崩溃 | 无孤立消费，无无预留的可发操作 |
| 接纳响应丢失 | 事务提交后断开客户端 | slot 不产生第二个 operation |
| 派发不确定 | 标记后崩溃、发送后断线 | Unknown 保留，重试符合契约 |
| 取消 | 排队取消、在途取消、取消后晚到回执 | 仅已排除收费的预留可退回 |
| 计费 | 无业务效果但收费、去重重试收费、晚到费用 | actual 受 C+R+Q 覆盖 |
| 授权 | 审批后改参数、接纳前撤权、历史 epoch | 网关当前授权及描述匹配 |
| 并发 | 两分支抢同一额度、分支取消与 join 竞态 | 根预算无双重分配 |
| 恢复 | 旧 checkpoint、重复事件、模型重新采样 | 许可不复活，resample 有新成本 |
| 版本 | 检查和写入之间修改、版本 ABA | 端点条件写入或明确拒绝保证 |
| 证据 | 重复、错 attempt、冲突终态、部分账单 | 幂等结算，不能把非最终证据当退款依据 |
| 适配器 | 隐式重试、失效去重 key、错误只读标注 | 契约违反能被检测并限制后续执行 |
| 数据流 | 摘要、缓存、子任务和日志外发 | 实际出口遵循接收方规则 |

先做单故障定位，再做成对交互，最后对“取消＋发送后崩溃＋晚到费用＋重试”的组合运行有界调度。每个结果记录故障数和调度范围。随机种子测试与穷举不互相冒充。

当前已实现一个联合协议切片及生成调度：固定一操作、两次尝试、派生授权、祖先撤权、一次崩溃/恢复和独立迟到收费。模型对全部有界可达状态检查不变量，真实 Store 则运行明确覆盖分组下的 194 条调度，另做十个进程退出情形；详细覆盖、排除项及原始证据见 [组合验证规格](24-combined-protocol-validation.md)。这属于 RQ1 的有限证据，不用于估计真实任务完成率或语言开发收益。

## 指标和统计单位

主指标 `SafeTaskSuccess` 为全部分配任务中“目标完成且整个规定可观察轨迹无违规”的比例。拒绝、超时、永久未决和执行失败都保留在分母。

并列报告正常成功率、每次违规类别、攻击成功率、误拒率、人工审批数、最终未知比例、预算占用率、实际成本、p50/p95 延迟、源码修改量和总修复时间。增加全拒绝对照，确保它安全但不会成为任务成功冠军。

开发实验的主单位为任务与开发者或 coding agent 配置；多次重复是层级观测。按任务或攻击族做配对聚类区间，报告绝对差异和原始计数。若任务很少，不用大量重复运行伪造大量独立样本。

先用小规模预实验估计方差及任务内相关性，再基于最小有意义收益计算样本量。预实验只用于设计，最终测试集冻结。若无法获得足够人类开发者，应将结论明确限于 coding agent 实验，不外推人类开发体验。

`pass^k` 表示 k 次都成功的可靠性，不能与至少一次成功的 `pass@k` 混用。零观测违规伴随样本量、采样单位和区间；有限状态穷举则报告边界和完整可达状态数，不用经验置信区间伪装其覆盖范围。

## 消融设计

去掉静态 affine 检查但保留账本，观察错误发现是否更晚以及修复成本是否增加。去掉清晰诊断但保留类型规则，分离诊断可读性的作用。把模型上下文长度和示例数量作为单独因素，检查生成成功是否主要来自更多提示。

将取消即退款、历史授权复用、按 operation 只预留一次费用、客户端检查代替原子版本条件作为故意损坏的变体。它们用于检验测试能抓到目标错误，不能当作代表现有最佳系统的主基线。

## 实施里程碑

| 阶段 | 交付 | 验收条件 |
| --- | --- | --- |
| M0 语义冻结 | 类型、状态、slot 规则、适配器契约、错误表 | 原方案和新增反例均能由规范解释，无状态含义冲突 |
| M1 受检 IR | 序列化格式、解释器、假的模型及模拟端点 | 所有外部请求经同一接口，拒绝伪造受保护值 |
| M2 持久运行时 | 单协调器、账本、outbox、恢复与对账 | 每个提交边界故障注入通过，实际模拟外部状态无目标违规 |
| M3 Python SDK | 构造 IR、类型提示、相同诊断 | 与手写 IR 的轨迹和错误决定一致 |
| M4 AL-0 前端 | parser、资源与效应检查、源码映射 | 正反例覆盖全部核心规则，合法同义程序与 SDK 一致 |
| M5 组合验证 | 结构化并发、动态计划、性质生成和语义对应 | 交互故障及重放测试通过，证明完成情况可审查 |
| M6 因果实验 | 冻结任务、同运行时基线、消融、报告 | 决定扩展语言或收敛到 IR/SDK |

单名熟悉编译器与数据库的工程研究者可暂按 10–14 周估算到 M4 的研究原型，M5/M6 另计；这只是规划假设，不能作为已承诺进度。未选择维护者和真实适配器前，不给生产发布日期。

Rust 仍适合检查器和长期解释器实现，但本轮环境未检测到 cargo，当前模型用 Python 标准库运行。设计研究不需要先安装工具链。未来实现应先复用受检 IR 协议，再选择具体语言版本和依赖。

## 必须保存的实验产物

真实 Git 发布轨道已有[可执行配对评测器](48-paired-git-evaluation.md)：支持 AL-0 与带生成绑定、固定 mypy 和共享 IR 检查的 SDK 提交，使用本地真实 Git 端点、回复丢失及进程退出调度、独立引用 oracle 和错误对照。参考答案校准只验证评测链路；它尚不构成 RQ2/RQ4 的开发收益实验。

每个实验保留任务版本、系统配置、代码及 IR、政策和适配器版本、事件轨迹、独立外部状态 oracle、费用世界记录、故障计划及最终判定。模型调用记录足以重建输入输出与成本即可，不需要私有思维链。

相同故障调度在不同实现上的语义位置应对应，例如“网关接纳后、端点回复前”，而不是硬编码相同毫秒数。性能实验单独运行，排除调试日志或故障注入的额外开销，并同时报告运行时开销和端到端耗时。
