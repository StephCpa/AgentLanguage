# 持久任务作用域与责任接管

更新日期：2026 年 10 月 25 日。实现位于 `al0/tasks.py` 和 `al0/concurrency.py`，调用原有 Store、预算分配树及共享 IR 解释器。本节记录宿主任务接口；后续增加的闭合任务 IR、句柄检查和推测执行见 [任务 IR 与推测执行](12-task-ir-and-speculation.md)。

## 身份、控制状态与责任归属

每个 scope/task 有持久身份、父节点、父内唯一的 key、固定程序指纹及独占预算分配。`open_scope` 从宿主选择的非任务分配划拨预算；`spawn_task` 从父 scope/task 划拨预算。任务插入与划拨在同一事务内提交。相同 key、程序和额度恢复同一任务；改变参数被拒绝。

任务的两个状态维度分别回答不同问题：

| 维度 | 状态 | 含义 |
| --- | --- | --- |
| 本地控制 | Ready、Running、Waiting、Completed、Failed、Cancelled | 是否开始、是否在执行、是否等待外部结果、是否已有本地终态 |
| 控制权与责任归属 | Attached、Joined、Runtime | 父节点仍持有控制句柄、控制句柄已收回且当时无未决责任、未决责任已登记给运行时 |

Scope 根使用 Open，关闭后为 Completed 或 Cancelled。`Runtime` 是持久接管记录，不会在后续结算时改写成 Joined；查询 `obligations` 才能判断当前责任是否已清空。这保留接管历史，同时避免把历史状态误读成当前费用仍未结清。

任务正常返回可以同时有业务 Unknown 或未结账单。`join_task` 收回本地控制权、取消未派发操作、归还自由余额，并将仍未决的责任登记给运行时。它不保证远端效果终止。Running 或 Waiting 不能直接 join，调用方须显式 `handoff_task`；该操作取消任务及子树的新工作，并进行相同的责任处理。

父任务返回前必须消费其所有子任务控制句柄。正常 `close_scope` 要求所有子任务已经 join 或 handoff。异常退出则按树的后序取消与接管。`finish_run` 同样拒绝仍持有 Attached 任务或作用域的运行，避免把未处理的控制句柄藏在 CompletedClean 后面。

## 任务命名空间与恢复代次

子任务仍使用同一个 run 和根预算。其 slot 是 `(run,node,activation=task_id)`，授权恢复键包含 task_id 和节点类别。两个子计划都叫 `answer` 的节点因而是两个独立操作；恢复同一 task 则继续使用原有身份。

任务程序指纹单独固定，不要求每个子计划与宿主控制程序指纹相同。解释器重新检查子计划并核对任务指纹。任务结果以 JSON 数据及检查回执引用持久化，Completed 的恢复读取该结果，不再重新执行计划。这个已完成任务结果与顺序解释器读取最新状态后重建返回值的行为不同，接口明确保留这一区别。

`claim_task` 返回 `TaskLease(task,epoch)`。同一个 Running 任务不能被普通 claim 再次领取。可信监督者确认需要恢复时，可显式使用 `recover=True` 更新 epoch；旧工作线程随后不能接纳、派发、重试或提交本地完成结果。这里没有根据超时自动取得重发权的规则。

恢复只改变工作线程的控制代次，不改变 task_id、slot、operation 或 attempt。已暴露但结果未知的 attempt 继续保持 Unknown。进程崩溃后即使还没有实际调用到提供方，也不会仅凭本地缺失回复重新发送已经取得派发权的 attempt。

TaskLease 是可信宿主的代次令牌，不是远程认证凭据。宿主及数据库仍在可信基中；不能据此宣称恶意 Python 插件隔离或分布式工作节点的安全认证已经完成。

审计修复后，嵌套 join、handoff、close_scope、异常退出和已有 scope/spawn 的恢复也校验当前父 lease。可信宿主若要越过父工作线程执行取消，须显式使用 `supervise_task` 或 `supervise_scope`，且不能处于工作线程资源访问上下文；它们不是失效 lease 的自动回退路径。语言 handoff 返回带标签的 task/state/disposition 回执，内部快照只供可信 Store 调用者读取，详见[审计修复](46-audit-remediation.md)。

## 作用域退出的事务边界

任务接纳和派发都会核对任务状态、预算归属和当前 epoch。退出、接纳、派发共用 Store 的事务串行化边界。

- 若退出先提交，新接纳或派发被拒绝，未派发预留归还。
- 若接纳先提交、派发尚未发生，退出事务取消排队操作并归还其预留。
- 若派发先提交，退出保留该 attempt 的费用责任，业务仍可能发生。后续业务回执和账单按原身份登记。

取消不强行终止 Python 回调或已经被网关接纳的外部请求。旧回调可以返回并递交真实费用，但不能据此覆盖新任务控制状态或继续获得新的派发权。这与原设计的网关接纳线性化语义一致，不构成端点执行时撤权保证。

任务拥有的分配禁止通过普通 `split_budget`/`join_budget` 绕过任务生命周期操作。嵌套任务使用 `spawn_task(parent_task,...,parent_lease=...)`。任务合并只转移 F，未决 R 和退休 Q 留在原资金归属下；迟到退款仍沿分配树归还开放祖先。

## Python 并发入口

```python
with TaskScope(broker, run, principal, 'summaries', {'units': 4},
               max_workers=2) as scope:
    left, left_future = scope.spawn('left', plan, {'units': 2}, grants)
    right, right_future = scope.spawn('right', plan, {'units': 2}, grants)
```

TaskScope 启动本地线程池运行受检子计划，正常退出时等待所有子任务并收回其控制权；遇到 Suspended 则登记接管。退出观察按 Future 完成顺序进行，任一子任务失败可以及时取消仍在阻塞的兄弟任务，不因等待更早 spawn 的任务而延迟观察错误。

作用域体或子任务抛出异常时，先提交整个作用域的取消与接管，再请求本地线程池取消尚未开始的工作。已经进入适配器的回调可能继续运行；线程池容量只约束本地线程，不等于远端作业并发上限。进程退出也可能仍需等待正在运行的 Python 线程，这是当前宿主实现的限制。

同一活跃 TaskScope 内重复 spawn 同一 key 返回相同 Future。重开已经完成的作用域，只允许恢复已有子任务；读取完成结果不会增加费用。故障后 Running 的子任务须由监督者显式恢复；未接管的 Waiting 子任务可以在收到回执后再次执行并读取原操作结果。

自动化后台监督、租约失效检测、进程级 worker 隔离和跨机器调度尚未实现。持久状态足以供监督者恢复，但进程被杀后不会由本库自行启动新的工作进程。

## 验证与示例

任务专项测试覆盖 33 个情况，包括并行同名节点、重复 spawn、嵌套生命周期、资金原子性、父子返回约束、接纳/派发与退出竞态、旧 epoch 拒绝、真实线程仍运行时的取消、迟到收费和异常传播。

`tests/task_worker.py` 使用独立进程退出，覆盖 spawn 提交前后、scope 关闭提交前后、任务派发后、本地返回值提交前后。派发后的恢复保持 Waiting 且不再次调用适配器；返回值提交前后的恢复均复用已记录调用或已完成结果。

```powershell
python -m unittest tests.test_tasks -v
python -m examples.parallel_tasks
```

示例使用两个本地模型调用，并通过屏障确保二者都进入适配器。两个相同子计划分别完成；根预算 10，确认费用 2，余额 8，预留 0，状态为 CompletedClean。恢复作用域和子任务后新增事件为 0。它验证并行身份及重放，不测量真实模型质量或性能收益。

schema 升至 5，支持从 2、3、4 迁移。新增任务表不会给历史普通操作伪造任务归属，也不更改原有操作和预算。v4 迁移测试保留子分配、未知操作及其预留；旧版已验证的非任务入口继续使用根或宿主指定分配。
