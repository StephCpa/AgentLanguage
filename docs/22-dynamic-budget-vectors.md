# 运行时预算向量与持久金额选择

更新日期为 2026 年 10 月 25 日。工作流现在可以根据受检输入、纯计算或工具结果计算资源数量，再用于预算拆分、作用域和子任务分配。首次选择的向量持久化，恢复继续使用原金额；账本仍独立检查资源归属与可用余额。

## 数据与资金分开

`resources` 从已定义的 Int 值构造资源向量：

```text
fn allocation(units: Int) -> Json {
    let one: Int = 1;
    let total = add(units, one);
    let amount = resources({u: total});
    return amount;
}
```

这是普通数据计算，不分配资金，没有预算效应。结果 schema 为 Json；若任何数量来自 Candidate，结果仍为 Candidate；否则含 Observation 时保持 Observation。对 Checked 数量做新构造不转移旧 artifact 的检查回执。标签按所有数量及当前控制上下文合并。

向量可以复制、传给纯函数、通过任务传递，或作为循环的数据状态。这些行为不会复制余额。真正的资金接口仍是不可复制的 Budget；它只由账本分配、受检调用或分支建立。

每个资源数量必须是 `0..2^63-1` 范围内的整数。布尔值、浮点数、负数和过大整数均拒绝。算术溢出在纯计算时失败，不通过截断、取模或浮点近似进入账本。resources 的结果同时受已有的 1 MiB 纯值大小限制。

## 三个动态分配入口

| 操作 | 动态形式 |
| --- | --- |
| 从当前资金划出预算 | `split_budget(amount)` |
| 从指定 Budget 划出预算 | `split_budget_from(parent, amount)` |
| 创建任务作用域 | `scope(amount, false)` |
| 创建无输入子任务 | `spawn(group, worker, amount)` |
| 创建带显式输入的子任务 | `spawn_with(group, worker, amount, inputs)` |

这些位置继续支持原有的 `{u: 3}` 字面量。动态形式必须引用一个先前值，接受 Json 或全部字段均为 Int 的已登记记录 schema。Json 的实际形状和数量在消费位置检查。向量包含的每个资源维度必须存在于父分配，即使请求量为零也不能凭空增加一个维度。

源码中的 `amount` 是值引用，`"amount"` 不是引用。SDK 的 split_budget、scope 和 spawn 接受字面量字典或同一 builder 的 Ref；`PlanBuilder.resources(name, entries)` 建立动态构造。IR 保留原操作，金额字段为字典时表示字面量，为字符串时表示受检节点引用。新增 resources 节点包含 `entries: {resource: reference}`。

预算消费者接受来自候选或观察的合法向量，并不宣称该额度具有业务正确性。父预算和授权边界始终限制实际支出；需要业务审批或额外校验的工作流应显式执行对应协议。

## 首次金额选择

schema 14 新增 budget_evaluations，键为 `(run, activation, node)`，保存 purpose、amount 和控制标签。purpose 区分 split、scope 与 spawn。每个循环迭代及嵌套调用拥有不同的稳定 node 路径；不同任务还有独立 activation。

动态入口依次执行：

1. 求得向量值，将来源标签加入当前控制上下文。
2. 若该位置已有金额记录，恢复原 amount 和标签；否则验证向量并提交首次记录。
3. 把当前控制标签与历史标签合并，将选定 amount 交给原有 split/open_scope/spawn_task 事务。

旧记录不会因为重新计算得到更大或更小的值而改变。业务状态从 Unknown 变为 Applied 后，某个表达式可能从 2 算出 4；同一分配位置仍使用首次选定的 2。新迭代、新调用位置或新 run 可以作出新选择。根输入、受检调用实参和保护资源各自已有的持久绑定约束仍然生效。

这是金额求值与资金转移两个独立步骤。金额记录本身不扣减余额、不接纳操作，也不创建任务。若父预算暂时不足，分配会失败，但首次金额仍被保留；以后余额足够时可以用同一金额重试。若业务希望选择更小金额，应进入另一个明确的分配位置，而不是修改历史。

现有宿主 `Store.split_budget` 仍要求同一 key 的父分配和金额精确一致。解释器先恢复金额，再调用账本；它不会要求账本接受一次已完成转移的不同请求。

## 崩溃和标签

| 中断位置 | 恢复含义 |
| --- | --- |
| 金额记录提交前 | 没有完成该位置的金额选择，可重新求值；还没有该位置的资金转移 |
| 金额记录提交后、分配前 | 沿用原金额与标签，再尝试分配 |
| 分配或任务创建提交后 | 恢复原 allocation 或 task，不再次转移资金 |
| Budget 已归还或任务已结束 | 恢复历史引用及结果，不重新开放已关闭的分配 |

恢复不会跳过到达该入口之前的所有程序计算；那些节点仍遵守自身的纯计算、操作重放和控制记录规则。新出现的上游错误仍可能阻止执行到达该位置。

金额数据的标签不仅留在向量上，也进入 Budget 结果、scope/task 控制上下文及后续工具出口检查。私密金额影响任务创建或是否能付款，因此即使工具参数是公开常量，也不能忽略金额的控制依赖。金额恢复保留历史标签；更严格的当前控制上下文也不能被旧记录放宽。既有任务控制记录若不匹配，仍会拒绝恢复。

任务内首次求值要求当前 worker lease；旧 worker 不能创建新记录。新记录还检查当前 run 生命周期。历史记录可读不意味着旧 worker 获得分配或派发权限，后续账本和任务操作继续复核租约。

## 资源性质

对于任意合法运行时向量 q，split 的逐维变化仍是：

```text
F_parent' = F_parent - q
F_child'  = q
Σ F_allocation' = Σ F_allocation
```

只有父分配各维余额均足够时才提交。计算、复制和持久记录 q 对账本是零变化。每个持久转移 key 至多创建一个 allocation；首次金额记录使恢复时重新计算的值不能改变该 key 的请求。

动态金额也不改变未决费用语义。任务挂起或作用域退出后，已暴露操作保留 reserved；归还只移动 free。迟到退款沿原分配父链进入最近仍开放的祖先，不因局部计算或任务状态变化另建余额。

这里给出的是转移规则和证明义务，尚未完成全语言类型保持或组合协议的精化证明。完整目标及证据边界见 [形式语义](04-semantics.md) 与 [实现状态](08-implementation-status.md)。

## 实测证据

```powershell
python -m examples.dynamic_budgets
python -m unittest tests.test_dynamic_budgets -q
```

[源码](../examples/dynamic_budgets.al0) 与 [SDK](../examples/dynamic_budgets.py) 生成相同 IR。输入 units=2，纯函数计算 `{u:3}`，随后依次用于 scope、子任务及任务内 split。三次转移都在同一分配树中，没有增加根预算。emit 调用一次，确认费用 1、预留 0、根余额 9；金额记录三条，恢复新增事件为 0。

28 项专项测试覆盖静态数量类型、运行时向量校验、零和最大整数、多维预算、未知资源、局部余额、标签、首次数量选择、并发、主体与租约、循环迭代身份、业务状态变化后的三个分配入口、任务等待与迟到退款、源码/SDK 等价及 v13 迁移。

九组独立进程崩溃覆盖 scope、spawn、局部 split 的金额记录提交前后，以及对应资金转移提交后。恢复均只有一次外部调用、三条金额记录和三条拆分，最终可用余额为 9。后续 [受检资源包](31-checked-resource-bundles.md) 已支持仿射句柄跨任务和多资源正常返回；循环资源状态、完整进程资源隔离和真实工作负载收益实验仍未完成。
