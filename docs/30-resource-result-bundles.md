# 具名资源结果包：下一阶段接口设计

状态：命名包、依赖类型、嵌套参数及正常任务返回已在 [受检资源包](31-checked-resource-bundles.md) 实现；后续 [资源任务结果](32-resource-task-outcomes-and-race.md) 已接通 TaskOutcome 与 race；一般业务资源分支已在 [受检业务 Variant](34-checked-business-variants.md) 实现，固定次数资源循环已在 [受检资源循环](38-checked-affine-loops.md) 接通。下文保留整体设计，不把尚未实现部分计作验证成果。

## 要解决的问题

在本设计提出时，任务已可同时接收 Permit、Operation 和 Budget，但只能返回一个 Operation 或 Budget。一个任务若需要返回“检查结果、尚未消费的 Permit 和剩余预算”，不能靠多个独立 join 完成：它们必须属于同一个持久决定；Permit 还必须绑定返回包中明确的 Intent。

下一阶段让数据与多个资源作为一个仿射结果交付，继续使用 schema 17 的原子资源清单和 Escrow。新增的是类型接口、组合值表示、静态拆包和运行时描述验证，不重建另一套转移账本。

## 包的类型和使用规则

拟议构造与拆包形式如下，具体源码语法需与现有 parser 统一后冻结：

```text
pack {
    note: Text,
    request: Intent<"send">,
    permission: Permit<request>,
    funds: Budget
}
```

1. 包含任一仿射资源的包整体是仿射值。pack 消费成员中的 Permit、Operation、Budget 及嵌套资源包；数据、Intent 和 Cap 不因此获得额外权限。
2. 同一资源不能通过两个字段、嵌套路径或原变量同时进入包。检查器验证 SSA 来源，运行时再按 kind/id 检查整包唯一性。
3. 解包一次性消费包并产生各字段的新 SSA 引用。普通 record/field、JSON 编码和任意字段投影不能复制资源。读数据字段的便捷语法可以由“完整解包后使用数据字段”展开。
4. Operation 和 Budget 字段分别恢复处理义务。Permit 允许仿射丢弃，但丢弃不得退回资金、复活已消费许可或创建新授权。
5. 导出的 Permit 必须在同一包内包含其绑定 Intent。类型使用规范化字段路径表示依赖，不能沿用子程序的局部变量名。运行时比较实际完整 Intent，不能只比较工具类型。
6. 包中的普通数据仍须通过 Catalog schema 验证，Checked 字段仍核对原检查证据；不存在“包已经受检，因此所有数据都可信”的转换。

相同字段类型但不同局部 SSA 名字的两个返回分支应当兼容；不同 Intent 依赖结构的包不兼容。规范化时按字段路径表达依赖并拓扑检查，拒绝悬空引用和依赖环。

## 持久描述与恢复

持久包至少包含受检接口描述、普通字段记录、资源字段路径到 ResourceRef 的映射，以及各字段标签和包控制标签。接口描述属于程序指纹覆盖范围。字段路径与普通数据名称分离编码，避免嵌套字段和外层参数发生名称碰撞。

发布前核对完整结果类型、资源种类、实际工具与 run、Permit/Intent 配对、权限表、所有权与 generation。普通值和整包资源在同一个 finish_task 事务中固定；不能先保存数据结果，再单独转移资源。

接收方依据固定返回记录生成新的整个包。所有资源在一个 join 事务中接收；其中一个字段无法接收就回滚整包。重放从历史接收回执恢复旧包，即使包中的某个资源后来再次转移，也不更新该字段的 generation。

资源转移检查权限表的包含关系；grant 已撤销与资源无法接收不是同一条件。撤销必须阻止新增接纳和派发，但不应阻止接收已存在的操作责任或归还剩余预算。后续使用仍重新检查当前授权。

原始 ResourceRef 记录只描述引用。调用者仍需通过当前 actor、TaskLease、权限表和资源代次检查；反序列化包不会把任意数据升级为执行权限。

## 结果分支与 race

| 情形 | 拟议资源责任 |
| --- | --- |
| 正常完成 | 发布成功分支声明的包，父方显式接收 |
| 程序显式返回的拒绝/失败值 | 可通过一般带资源 sum type 发布该分支声明的包，例如返回未消费 Permit 与 Budget |
| 解释器异常、worker 失败 | 由 Runtime 接管当前仍持有的资源；不能猜测原输入中哪些字段尚未消费，再伪造一个静态失败包 |
| Waiting / Cancelled | 暴露操作的费用责任继续存在；观察记录本身不重新授予操作控制权 |
| race 胜者 | 在固定 winner 的同一事务中接收完整包；其他候选当前持有的资源进入取消/接管路径 |

显式业务失败与执行器异常必须分开。前者由程序构造受检分支结果；后者的执行位置可能落在接纳、费用或外部效果之间，只能报告已持久化的责任，不能恢复原输入包。

race 候选必须具有相同的规范化包接口。胜者选择、完整资源接收和败者责任处理必须形成可恢复的一次决定；不能先暴露 winner 的某个资源，再异步决定余下字段。完成、失败、取消和胜负选择的控制标签继续合并所有相关候选的标签上界。

## 受检 TaskOutcome 的接入约束

以下规则来自对 `take_task_outcome`、`cancel_outcome`、`select_race` 和分支检查器的逐项检查，后续已在 [资源任务结果](32-resource-task-outcomes-and-race.md) 接通。一般业务 Result 的封闭类型机制后续已在 [受检业务 Variant](34-checked-business-variants.md) 实现；终态 infer_result 后续已在 [受检推理结果](36-checked-inference-results.md) 接入，未决与接纳层结果仍待完成。

`TaskOutcome<T>` 是执行状态分支。仅 Completed 携带 T；Failed、Waiting、Cancelled 携带状态与责任说明，不携带从原输入推测出的资源。一般业务 `Result<Success, Rejected>` 是另一层类型：任务可以正常完成并返回业务拒绝包，不能把执行器异常直接转换成该包。

当 T 为 Operation、Budget 或 Bundle 时，Completed 分支必须声明 `result` 参数，即使它最终只打算交接或归还资源。`match_task` 消费该 outcome；重复匹配、普通字段投影、普通 JSON 参数及持久数据快照均不能复制其资源载荷。接入前的检查器只清除“尚未匹配”义务；资源接入已增加“已经消费”的检查。分支处理完资源后可以返回普通数据，不要求失败分支凭空构造同一资源包。

正常结果接收需在同一事务中完成：检查父 actor 与 TaskLease、接收全部 Escrow 资源、按固定接收回执重建值记录、释放子任务控制句柄、保存 outcome。值记录保留 bundle/resource 元数据和标签；现有只接受 data/receipts/label 的结果规范化不能直接用于资源结果。若任一字段无法接收，整项决定回滚。重放读取该决定保存的旧代次，不能查询当前 owner 来更新引用。

取消接收已独立于原来的“先 handoff，再 take”组合。在当前实现中，handoff 可以保留 Completed 状态，同时将尚未接收的资源退役；随后读取 Completed 并不能授予这些资源。后续实现的顺序为：

| 原子决定读取的状态 | 资源结果语义 |
| --- | --- |
| 已完成且返回包仍可接收 | 完成胜出；接收整包并固定 Completed |
| 尚未完成、包括 Waiting | 取消胜出；接管当前剩余责任并固定 Cancelled |
| 已失败或已取消 | 保留终态说明，不重建输入资源 |
| 已经存在该任务的 outcome 决定 | 重放原决定及原接收代次 |
| 完成包已由其他 handoff 退役，且没有可重放决定 | 拒绝资源接收，不把历史 Completed 当作可用包 |

取消先提交后，旧 worker 不能再发布成功包；完成先提交但取消接收尚未提交时，事务内退出不能留下半接收结果。已暴露请求的账单、原 attempt 出资归属和迟到回执在两种顺序下都继续有效。单独 handoff 仍表示放弃接收并交接责任，不能据此重新制造可接收的资源结果。

race 的事务还需固定候选集、胜者与整包接收回执，并处理所有败者的当前责任。胜者权限或接收校验失败时，不能提前提交胜者记录，也不能已退役败者的一部分资源。重放依据历史胜者及固定接收回执恢复结果；结果标签合并所有候选的标签上界。此规则没有放宽推测作用域原有的行动限制。

接入验收应新增：成功分支漏接及重复匹配拒绝；成功/取消两种提交顺序；嵌套父 TaskLease 过期；整包接收中途退出；决定提交后但解释器返回前退出；已接收成员再次转交后的旧 outcome/race 重放；败者已暴露操作的迟到费用。上述情形需分别用真实 Store、独立端点与物理进程退出验证，不能计入当前资源包的 31 项专项测试。

## 实施顺序与验收

第一步在共享 IR 实现 pack/unpack、规范化依赖类型与仿射义务，然后扩展 SDK 和源码；既有单资源返回作为等价的一字段接口保留。第二步接入持久包序列化、TaskRunner 发布及 join 重建，最后处理一般带资源 sum type、TaskOutcome 与 race。循环资源状态复用同一类型和记录形式，但需要另行验证迭代身份与单次转移。

必须覆盖以下可观察行为：

- 同一任务返回数据、未消费 Permit、其 Intent、Operation 和 Budget，父方分别使用或交接，费用始终归原 attempt。
- 从 pack 到 unpack、嵌套包、分支及任务之间的重复别名拒绝；错误 Intent 路径和实际不同 Intent 拒绝。
- 发布/接收事务内与提交后的进程退出、重复 join、部分成员再次转移后的旧包重放。
- 包内某字段不再由暂存区持有或越过接收方权限表时的整包回滚；撤销后允许责任交接但禁止新行动，已暴露请求的迟到费用不被取消吞掉。
- 字段标签、包控制标签和失败/race 标签均不因序列化或拆包丢失。
- 源码与 SDK 产生同一 IR；安装包外部执行以及真实 Store/独立端点验证覆盖完整流程。

这些验收不能用当前单资源返回示例或已有有限模型代替。真实工作负载与同运行时 SDK 对照仍是后续研究阶段的独立要求。
