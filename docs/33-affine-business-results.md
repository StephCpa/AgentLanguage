# 一般业务资源结果：封闭 Variant 设计

状态：封闭类型、构造/匹配、持久值与跨任务接收已在 [受检业务 Variant](34-checked-business-variants.md) 实现。本文保留整体设计；终态 infer_result 后续已在 [受检推理结果](36-checked-inference-results.md) 接通；固定次数资源循环已在 [受检资源循环](38-checked-affine-loops.md) 接通；未决/接纳层结果仍待实现。已有 [TaskOutcome/race](32-resource-task-outcomes-and-race.md) 解决执行状态与资源接收。

## 目标场景与分层

同一个提交工作流可能正常返回以下三种结果：

| 分支 | 载荷 | 资源含义 |
| --- | --- | --- |
| Accepted | Bundle(operation: Operation, funds: Budget) | Permit 已消费，返回操作责任与剩余资金 |
| Deferred | Bundle(request: Intent, permission: Permit&lt;request&gt;, funds: Budget) | 接纳尚未成功，保留原许可与其绑定请求 |
| Denied | Bundle(reason: Text, funds: Budget) | 没有可返还的有效许可，仍返回声明的预算 |

上述任务在执行器看来都可以 Completed。worker 异常、Waiting 和取消仍由外层 TaskOutcome 描述，不自动选择业务分支，也不推测资源载荷。实际类型关系为 `TaskOutcome<Variant<Accepted: A, Deferred: D, Denied: N>>`。

业务标签由受检程序构造，但标签名称本身不证明外部系统状态。需要证明未产生外部效果时，仍须依靠操作状态和相应检查证据；一个名为 Denied 的普通分支不能清除已暴露请求的费用责任。

原始方案中的 `Result<Candidate<T>, InferenceError>` 也应使用同一封闭类型机制。普通数据 Variant 和资源 Variant 都属于本阶段范围；前者保留 Candidate/Observation/Checked 的来源与证据类别，不把成功解码提升为业务正确。终态模型错误分类已通过后续 infer_result 接入，未决与接纳层结果仍待补齐；网络超时或未结算费用不能被一个普通 Error 标签消除。

## 封闭接口

采用结构化、封闭的 Variant：接口显式列出全部标签与每种载荷类型。接口身份由排序后的标签、各载荷完整类型、证据要求及封闭依赖共同决定；不含构造工作流的局部 SSA 名字。

第一版只允许现有可跨工作流传递的封闭载荷：普通数据/检查证据、Cap、Operation、Budget、Bundle，以及递归 Variant。裸 Permit 不作为载荷，因为它需要同一封闭接口内的 Intent；返还 Permit 使用现有依赖 Bundle。接口深度、字段/标签数量和编码大小沿用受检值的限额，不引入任意递归类型。

只要一个分支包含仿射资源，整个 Variant 就是仿射类型。即使本次运行选中不含资源的分支，静态值仍须匹配、移动或返回一次，避免同一接口的使用规则取决于运行时标签。纯数据 Variant 具有可复制语义，但不能以这个例外放宽任何混合资源接口。检查器需要依据完整类型判断仿射性，不能只依靠一个把所有 Variant 一概列为资源的 kind 集合。

源码可使用完整结构类型注解；类型别名只是后续减少重复的语法。SDK 应能显式描述接口，不应要求执行一个示例计划才能知道其他分支的类型。当前 Bundle 用已检查计划取得接口的便利方式可以复用为可选构造辅助，不作为 Variant 的语义定义。

## 构造与匹配的共享 IR

拟新增两个节点，命名与源码具体拼写在实现时统一：

```text
variant(id, interface, tag, input)
match_variant(id, input, cases, captures)
```

`variant` 固定完整接口和一个标签，验证 input 精确符合该标签的载荷类型。它只封装已有值：不创建预算、不产生授权、不移动数据库 owner。仿射载荷在静态环境中被消费；普通数据不能通过描述符伪装成资源。构造其他分支不会解除当前工作流尚未处理的资源义务。

`match_variant` 要求 cases 的标签集合与接口相等。每个分支显式接收自己的 `result` 载荷；所有捕获的仿射值必须在每个分支中接收并处理。资源型输入 Variant 被消费一次，载荷的 Operation/Budget/Bundle/嵌套 Variant 义务在选中分支重新出现。

分支返回类型仍必须相同。如希望各分支再返回不同结构，应显式构造同一个新 Variant 接口，而不是由检查器隐式合并结构。这样既有 `match_task`、`if` 与 `match_admission` 的返回类型规则无需变成依赖任意运行时数据的推断。

`variant` 和 `match_variant` 需要同时进入 IR 字段表、源码操作覆盖检查、SDK 公共接口类型验收及安装包消费例子。不能只在 Python 宿主返回带 tag 的字典，就称为语言已支持。

## 类型规则的实现约束

令 `V = Variant{tag_i: T_i}`。检查器至少需要区分以下性质，而不是把它们合并成一个“是否资源”的布尔值：

| 性质 | Variant 的判定 | 影响 |
| --- | --- | --- |
| 仿射性 `aff(V)` | 存在一个 `aff(T_i)` | 禁止整个值被重复移动或匹配 |
| 必须处理 `need(V)` | 第一版资源 Variant 取 `aff(V)` | 即使活动分支无资源，也需明确匹配、转交或返回 |
| 可跨边界 `portable(V)` | 所有分支载荷均为封闭、允许传递的类型 | 拒绝借用引用、Scope、Task、Unpacked 及未封闭依赖 |
| 可用于纯计算 `pure(V)` | 所有分支均满足现有纯参数约束 | 不能用“可复制”替代“纯”：Cap 可复制，但不是纯数据参数 |
| 受控入口 `controlled(V)` | 任一分支含需要受检入口的权限或资源值 | 即使 V 不仿射，也不能通过原始 JSON 参数导入 Cap 等权限载荷 |

构造 `inject(tag_j, x): V` 只按实际载荷 `T_j` 决定是否消费 x；若 `aff(T_j)` 为假，原普通数据仍可复用。但新产生的 V 按完整接口计算 `aff(V)` 与 `need(V)`。这是混合资源/数据分支最容易错误实现的地方：不能因为本次没有 ResourceRef，就把整个结果变成可复制值。

匹配规则将资源型 V 从外层可用环境移除，为每个分支分别引入该标签的载荷参数。各分支从相同的外层捕获接口出发独立检查；检查器不能把一个分支释放的资源，作为另一个分支已经释放的证据。所有分支通过既有处理义务检查并返回同一类型后，才产生外层结果。

实际载荷的子类型/证据接受关系沿用共享检查器的明确规则，并为每种关系提供正反例；禁止静默增加 Checked 谓词、改变工具名义身份或更换 Permit 所依赖的 Intent。封闭 Variant 接口相等仍比较所有分支的规范化结构，而不是只比较当前标签或当前载荷。

Broker 的入口判定不得仅使用 `aff(V)`。例如仅含 Cap 和普通数据分支的接口可以不仿射，却仍是受控入口；把它按普通 Json 接收会绕开现有 Cap 参数的来源限制。标签、权限表与检查回执的验证继续依据实际载荷类型执行。

## 值记录与持久资源清单

持久值记录包含 Variant 接口描述、选中标签和该载荷的完整值记录。资源枚举只遍历选中的载荷；未选中的类型分支没有实例，也不能贡献假资源引用。元数据不得藏在普通 data 字典里等待运行时猜测。

建议路径编码在现有字段路径基础上加入有类别标记的段，例如 Variant 载荷段与 Bundle 字段段明确区分，避免用户字段名等于标签或保留字时产生冲突。规范化规则在新接口内固定；不改写已存在 Bundle 转移记录的路径。禁止重复 kind/id 的规则跨 Bundle/Variant 嵌套继续适用。

TaskRunner 在发布前检查接口、标签、载荷和资源清单；spawn 保存固定输入模板；finish 将值记录与实际资源一起发布；join/TaskOutcome/race 用固定回执重建实际载荷。选中的分支可能没有任何资源，此时清单为空仍必须保留 Variant 元数据与仿射接口，不能降为普通 JSON。

资源型 Variant 的 Completed 分支必须接收 `result`，包括本次载荷恰好为空资源清单的情形。静态义务由完整接口决定，实际转移由选中载荷决定，两者不能混为一项判断。

当前 `record_refs`、`replace_record_refs`、`validate_record`、Value、Broker 参数检查和权限资源枚举需要共同扩展。不能只把 Variant 名字加入 `MOVED_RESOURCES`：这会漏掉空资源分支、嵌套值元数据、Cap 权限与 Intent 解码等边界。

运行时还须把原子资源与容器分开：Variant 本身没有独立的 custody 行，不能对容器调用 `resource_birth`。Scope 的隐式退出也不能只检查实际枚举到的 ResourceRef；资源型 Variant 即使选中空资源分支，仍需遵守其声明接口的显式接收/交接要求。

## 权限、标签和恢复

构造标签可以取决于模型输出、工具观察或私密条件，因此构造结果的标签合并控制上下文与实际载荷标签；匹配时先把整个 Variant 的标签加入控制上下文，再进入分支。不能通过投影 tag 公开一个私密选择，也不能因选中公共载荷而删除决定标签的私密控制依赖。

权限表检查递归遍历实际载荷中的 Cap、Permit、Operation。类型声明中的未选中分支不授予权限，也不要求为不存在的实例寻找 ResourceRef。引用重建仍使用固定转移回执；记录反序列化、分支标签和接口描述都不代替当前 custody/TaskLease 检查。

本地封装和匹配不单独变更 custody，但分支选择必须可重放。若标签来自已持久化任务/调用/Admission 结果，则使用固定结果；其他有副作用的匹配沿用首次分支选择和输入快照协议，不能在恢复后用新观察重新选择另一分支并复活已移动的资源。

## 实施与验收顺序

1. 实现封闭接口、构造/穷尽匹配、仿射义务及规范化依赖。覆盖所有资源分支、混合资源/纯数据分支、不同标签但相同局部名字、裸 Permit 拒绝及重复匹配。
2. 扩展值记录、Bundle/Variant 相互嵌套、权限/标签和固定资源清单。覆盖空资源活动分支、重复资源、未知标签、错误载荷、失配接口及模板代次。
3. 接入工作流调用、任务参数/返回、TaskOutcome 和 race。测试 Accepted 操作可处理、Deferred 许可只能对原 Intent 再接纳、Denied 预算能归还；解释器失败不能转换成任一业务包。
4. 用真实 Store 和独立端点执行三种分支，并在发布、接收、匹配快照及再次转交的事务中/提交后退出进程。验证固定分支、原代次、调用次数、费用与退款账户。
5. 同步源码/SDK IR 等价、类型正反例和外部 wheel 消费证据，再将循环资源状态接入同一类型体系。循环还需要独立验证每轮状态的唯一移动、迭代身份和检查点恢复，不能因 Variant 已支持就宣称循环已完成。

有限 custody 模型和真实运行时之间的完整对应仍是独立研究要求。新的业务标签与空资源分支必须进入后续模型覆盖清单，不能直接沿用现有模型的状态数作为新接口的验证成果。
