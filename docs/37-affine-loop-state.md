# 仿射循环状态：检查点与资源代次设计

状态：本文保留设计依据。固定次数 repeat 的资源状态与原子交接已在 [受检资源循环](38-checked-affine-loops.md) 接入 IR、SDK、源码和运行时；一般循环控制及完整形式对应仍待完成。

## 要解决的程序

一个工作流可能携带 Budget 多轮生成和检查候选，也可能携带未决 Operation 进行有界观察。循环次数固定或受限并不能保证资源安全：上一轮保存的 Permit、Budget 或 Operation 引用不能在下一轮继续作为有效别名使用，恢复也不能重新授予旧引用控制权。

已有 `loop_frames` 在同一事务中保存下一 index 和当前值；已有 custody 通过资源代次拒绝旧引用。二者尚未合并。仅把 IR 的 pure 类型判断改成允许 Bundle/Variant，会留下“游标前进但资源代次未前进”以及相反的中间状态。

## 静态边界

拟沿用 repeat 的结构，显式区分可复制状态与仿射状态的执行路径：

1. 循环初值与循环体 `state` 参数、返回值具有完全相同的封闭类型。需要不同业务形状时使用同一个 Variant 接口。
2. 若 state 是仿射类型，repeat 消费初始引用，产生一个新的状态引用；父计划不能再使用初值。
3. 循环体每次接收一个 state，所有资源义务须在本轮消费、明确移交责任或纳入返回状态。不能在失败分支猜测完整返还原输入。
4. 固定捕获仍只允许可复制的值。希望跨轮携带的资源必须纳入 state，避免把同一捕获向每一轮重复传入。
5. 零轮仍完成一次状态交接并返回；选中空资源分支的仿射 Variant 也必须经过接口消费检查，不能依据实际资源清单为空而退化成普通数据。
6. 纯函数仍不允许资源状态。局部步骤限额和协作期限保持原有规则，不能宣称循环上限提供完整 CPU 或内存隔离。

## 持久状态与事务

推荐保留资源的 Root/Task 责任主体，将循环阶段作为固定转移回执记录，不立即增加一种 Loop 责任主体。每次跨循环边界传递时更新代次，即使同一资源没有更换 kind/id；静态检查管理作用域，运行时通过代次阻止历史引用再次执行新操作。

需要新增或扩展的记录至少包含：循环身份、封闭状态类型、首次输入模板、入场回执、当前游标、当前值模板、当前资源清单与对应代次。Bundle 字段路径和 Variant 标签路径沿用现有编码，不能重新使用会发生字段歧义的拼接字符串。

### 入场

第一次进入仿射循环，在一个事务内验证初值中的所有实际资源、当前 owner 和 task lease，增加这些资源的代次，保存状态模板、入场回执和 index=0。恢复读取原回执，不能重新增加代次或把旧初值刷新成当前引用。

零轮也需要该记录，使初值消费与最终结果有明确恢复身份。若采用“零轮不移动”的优化，必须先证明它不会为零轮和多轮生成不同的别名规则；第一版不做此优化。

### 每轮提交

循环体用固定 `(循环身份, index)` 路径执行。其返回值只是待提交状态；提交事务同时执行：

- 核对 index 等于当前游标，返回的封闭类型等于状态接口；
- 逐一验证实际返回资源的持有者、代次和 Live 状态，拒绝重复引用；
- 增加返回资源的代次，将模板中的引用替换为新回执；
- 保存完整状态、标签和下一 index。

任意一步失败均回滚。游标已经前进时，旧一轮重放只能读取此前已固定的结果，不能再次移动资源。恢复不得通过 `resource_birth` 或查询当前最大 generation 来修复旧别名。

### 退出与恢复

完成的循环返回最后一次提交的固定状态；后续节点可以消费它。整段程序重放时，该状态回执可能已是历史代次，这与现有任务接收回执一致：它可用于重建既有节点，但不能支持新的资源操作。

如果在循环体内消费了资源、但尚未推进游标就崩溃，恢复必须重建同一轮的既有节点和它们的持久结果，最终提交真正返回的状态。不能简单地从旧 state 重新派发外部请求。循环体自身可以包含调用、子任务或嵌套循环，因此这条性质需要组合测试。

## 取消与未决推理

持有主体保留为 Task 时，取消仍由该任务的现有责任接管路径处理。取消和循环提交必须在同一存储同步边界上决定哪一方先发生：提交胜出时接管新代次；取消胜出时拒绝旧 worker 提交。不能只清理旧 loop_frames 中记录的代次而漏掉本轮已创建、尚未提交的新资源。

该协议也是可继续执行的 `Waiting(Operation)` 推理分支的前提之一。每次观察必须有独立的程序位置或循环 index，固定该次观察；Unknown 到终态的推进由后续观察完成。当前 `inference_results` 只保存终态，不应把第一次 Waiting 存入以 Operation 为唯一键的终态表，否则同一操作会永久重放等待结果。

## 实现前需要闭合的检查

资源最终接收后可能再次进入任务或嵌套循环，需要逐项检查解释器的引用登记、调用帧、旧代次回放和取消扫描。首版可复用 `_custody_move` 的条件更新，但必须为循环回执定义独立、稳定的身份；不能把任务返回表冒充循环进度表。

测试必须覆盖下列不同要求，不能仅验证正常多轮结束：

| 场景 | 必须核对的结果 |
| --- | --- |
| 0、1、多轮传递相同 Budget | 初值不可复用，最终余额与所有费用归属一致 |
| Permit 被消费后换为 Operation 分支 | 旧 Permit 不可恢复为可用，返回类型仍为同一 Variant |
| 本轮创建资源并返回不同清单 | 新资源正确进入下一轮，未返回资源义务不消失 |
| 空资源 Variant 分支 | 仍有接口级消费与返回义务 |
| 入场、代次更新、游标写入前后退出进程 | 资源代次与游标一起生效或一起回滚 |
| 提交成功后下游消费，再重放父计划 | 固定回执能重建历史，不能再次消费 |
| 本轮调用子任务或嵌套资源循环 | 多层交接均使用各自固定代次 |
| 取消与本轮提交并发 | 唯一决定有效，无两方同时持有，无遗漏责任 |
| 未决请求随后收到终态事实 | 不重复调用；后续观察可推进，迟到费用仍入原账户 |
| 源码与同运行时 SDK | 相同计划、资源变化与外部调用轨迹 |

循环边界的可信 Store 事务、固定回执及共享 IR、SDK、源码接口已按后续实现接通。形式对应仍需将循环游标与 custody 转移纳入现有有限模型，不能由局部测试直接推导完整守恒证明。
