# 推理接纳前结果：事务边界与接口设计

状态：本页保留实现前的设计论证。try_infer 的固定接纳/拒绝已实现，实际协议与验收见 [受检推理接纳](42-checked-inference-admission.md)。下文关于待实现步骤描述设计时基线；提供方拒绝及受检派发阻止也已接通，见 [后续实现](44-checked-inference-provider-outcomes.md)。

## 需要解决的问题

当前 infer_progress 先 authorize，再 admit，最后创建观察。预算拒绝已经可以在既有 admission_decisions 中固定，但调用者仍收到异常；授权拒绝可能发生在 Operation 甚至 Permit 产生之前，没有推理观察可用于恢复。直接捕获异常并返回 Error 会留下一个问题：恢复后权限或预算变化，原来被拒绝的位置可能重新发起调用。

拒绝决定必须在持久层固定，且不能要求先有 Operation。它与模型已经接纳后返回的 InvalidOutput/NoResult 不同，也不能当作 Unknown/Pending。后两者已有远端责任，不能安全地重新接纳。

## 建议保持分层结果

新增操作暂称 `try_infer`，不要悄悄扩大现有 infer_progress 的穷尽分支集合：

```text
try_infer(model, request)
    -> Variant<{
         Rejected: InferenceRejection,
         Started: InferenceProgress<Model,T>
       }>

InferenceRejection = {code: Text, tool: Text, version: Text}
```

Started 表示本地已接纳，内部可以是 Success、Error 或 Waiting；它不声称提供方已完成甚至已收到请求。调用者匹配 Rejected 后可显式采取其他计划；匹配 Started 后使用本轮已实现的三个进度分支。通过不同位置显式重试，不重新打开同一拒绝位置。

拒绝代码至少区分预算不足与授权不可用。信息流拒绝是否暴露给程序应与公开诊断策略一并确定。错误结构是普通数据，不是认证凭据，不应携带凭证、授权父链、私密参数或供应商原始响应。它的标签必须覆盖请求、控制上下文及所检查政策事实；是否允许暴露“某权限存在但已过期”应由宿主统一决定。

## 原子接纳决定

建议增加按 `(run, activation, node)` 索引的推理接纳决定，固定请求、工具版本、Catalog、授权选择及出资分配。先查历史决定并精确核对绑定，再进行当前生命周期与 worker fencing 检查。选择“没有 grant”也应形成明确的首次选择；不能在历史位置自动补绑新 grant。请求或调用环境改变时应拒绝重放，而非替换旧决定。

成功路径需要把授权产生的内部 Permit、原子接纳及成功决定放入同一事务。当前 authorize 自己开启事务，因此不能直接在外层事务中再次调用公开 authorize/admit：应提取不自行提交的事务内授权辅助函数，保留原公开方法的兼容包装，再调用既有 `_admit_in_tx`。这项重构必须单独回归旧授权键、Permit 来源、任务权限表与 custody 创建逻辑。

在 savepoint 内执行可恢复的授权/预算检查与资源创建。只有明确白名单内的本地拒绝可回滚 savepoint 后固定 Rejected；成功则一并固定 Operation。内部错误、SQLite 故障、程序/输入不匹配、运行停止、失效 TaskLease、越界 custody 和取消不能落入普通拒绝分支。拒绝后不把内部 Permit 暴露给用户，也不能留下一个可误用的 Live Permit。

当前 `_custody_created` 同时把出生引用登记到本次解释器访问上下文。数据库回滚后该引用不会对应任何 Live 对象，但新实现仍应恢复 savepoint 前的上下文映射，避免把失败接纳产生的临时引用长期记入解释器资源集合。成功提交后只公开成功分支需要的引用；资源 ID 的产生不等于接纳成功。

成功决定与推理观察可分为两个事务，因为成功决定已持久绑定唯一 Operation。崩溃在两者之间时恢复同一操作，不能重新 authorize/admit。拒绝决定没有 Operation、attempt 或费用预留。事务内获准但尚未派发时遭撤权，派发协议仍可阻止发送；不要将这个已经存在 Operation 的情形改写为接纳前 Rejected。

## 提供方拒绝单独建模

提供方明确拒绝发生于接纳后，可能已经收费。应通过可信适配器的结构化状态表达，并作为持久业务证据的一部分记录；模型生成的自然语言或任意输出字段不能自行宣称 Refused。业务与费用仍独立。

具体适配器封套及业务状态映射需先确定，再扩展 Error 的规范代码。超时、连接中断、空响应、格式错误、明确拒绝和无结果不能混并：连接中断保留 Waiting；格式错误保留 InvalidOutput；明确拒绝需要可靠的提供方状态。不能推断“不含输出”等于“不收费”。

## 验收矩阵

| 场景 | 必须验证的结果 |
| --- | --- |
| 无授权、过期、父授权撤销 | 首次拒绝持久；恢复不因新权限自动接纳 |
| 预算不足后补充可用额度 | 同位置仍拒绝；新位置可显式再试 |
| 两个位置竞争最后额度 | 至多一个成功预留；另一位置固定拒绝 |
| 授权插入、接纳、决定写入前后退出进程 | 无孤立许可、无双重预留、无重复端点调用 |
| 已接纳但未观察时崩溃 | 恢复同一 Operation 与原 attempt |
| 撤权/取消与派发或决定竞争 | 已接纳与未接纳责任不混淆；取消 worker 不能发布新决定 |
| 提供方明确拒绝但迟到收费 | Error 保留，账单仍按原 attempt 结算 |
| 私密输入与拒绝分支控制依赖 | 拒绝载荷及后继动作均保留标签 |
| 源码、基础 SDK、生成绑定、wheel | 相同 IR、固定结果、准确的静态反例 |

还应把接纳决定、观察代次和取消纳入已有有限模型，并选择生成调度检查真实 Store。单独增加顺序单元测试不能替代这些组合义务。完整语言与实验目标保持不变。
