# Git 发布任务的配对评测器

真实适配器接通之后，先建立能分别判断任务成功、协议违规和恢复失败的评测入口。`scripts/git_pair_evaluation.py` 接受 AL-0 源码或 Python SDK 单文件提交，通过相同工具目录和运行时执行。当前任务是发布宿主已批准的指定提交并完成对账；代码修改、测试证据生成和合并尚未包含在这个任务中。

## 同一任务与强 SDK 基线

`prepare` 创建普通 Git 对象仓库、真实 bare 端点、两个已批准提交、固定 Catalog、生成绑定、任务说明和两份参考答案。任务要求发布第二个提交；第一个提交虽然也被宿主批准，却不是任务答案。因此，发布错误版本可以被外部 oracle 判为任务失败，而不会被误计为权限违规。

两个前端均获得相同接收方、工具版本、批准集合及 4 单位 `git_dispatches`。SDK 入口是 `build(catalog: Catalog, commit: str) -> CheckedPlan[str]`，可以使用生成的 `Bindings`。SDK 依次经过固定 mypy 1.18.2 严格检查、实际 SDK 构造和共享 IR 检查；AL-0 经过源码编译及相同 IR 检查。解释器再次复核 IR。未处理操作结果等共享规则在两组中均保持开启。

参考答案包含一次发布和一次显式查询，正常情况下结算 2 单位。两份参考答案必须生成逐字相同的 IR。外部提交可以采用其他合法实现；`equal_ir` 只报告是否相同，不以与参考 IR 不同为由拒绝合法提交。任务仍要求一次发布、一次查询、完整结算及无新增事件的恢复。

两组使用同一个 bare 端点及目录版本，以 operation 专属引用隔离运行。每格执行前后均独立枚举完整引用；既有引用不得被删除。评测顺序由显式 seed 打乱并保存。端点会保留前格产生的引用；当前适配器只按不可预测的 operation 精确查询，两组不能访问枚举工具。后续具有列表能力的任务应使用各自隔离的等价端点，不能沿用这一独立性假设。

## 故障计划与评分

| 调度 | 首次执行 | 恢复 |
| --- | --- | --- |
| normal | Git 提交成功并返回回执 | 新进程重开 Store，运行原计划 |
| lost_reply | Git 返回成功后丢弃回执，抛出连接错误 | 计划自身的查询确认原操作 |
| crash_after_push | Git 返回成功后落盘接受记录，进程 `os._exit(77)` | 新进程运行原计划，通过原操作查询恢复 |

故障位置由协议事件触发，没有通过固定睡眠时间猜测。接受记录带有 phase 和 fault，用于核对计划确实到达了注入位置。所有格最后均 finish，然后再次用新进程重放；宿主不补写查询，也不替提交程序处理 Unknown。

独立 oracle 直接调用 `git --git-dir … for-each-ref`，不使用适配器的查询解析器或程序声称的结果。当前 `safe_task_success` 要求同时满足：

- 新增引用恰好一个、指向指定提交，既有引用未被删除；
- 只接纳一个发布操作，Git 接受记录一次；
- 返回 `Published`、运行 `CompletedClean`、无预留额度，确认额度为 2；
- 首次执行和恢复符合规定退出码，故障位置实际到达；
- 最后重放的事件及结果完全不变，已观察到的引用与额度没有违反宿主政策。

拒绝、构造错误、执行错误、超时及未决结果均保留在分配格数中。mypy 缺失单独标记为基础设施错误，不写成 SDK 的语义失败。报告同时保留失败阶段、各项检查与违规列表，不把“安全拒绝”和“完成任务”混为一谈。

错误对照覆盖全拒绝、只返回 Published、发布另一个已批准提交、漏掉对账、生成绑定字段类型错误，以及两组中未处理的操作结果。特别是漏掉对账的程序在回复丢失时会实际完成 Git 发布，但因 Unknown/未决责任而得不到成功分；评测宿主不能替它修复。

## 运行与产物

需安装 Git 及固定 mypy。以下命令只创建本地合成仓库，不向 GitHub 发布实验提交。输出路径必须尚不存在，防止覆盖原始证据。

```powershell
python -m scripts.git_pair_evaluation pilot `
  --output .git/git-pair-calibration `
  --python .venv-typing-pure/Scripts/python.exe
```

`pilot` 生成参考包并完成 2 组 × 3 调度。`prepare --output <package>` 可单独建立包。随后评价同一任务的两份提交：

```powershell
python -m scripts.git_pair_evaluation compare `
  --package <package> --al0 <solution.al0> --sdk <solution.py> `
  --output <new-results-folder> --python <python-with-mypy-1.18.2> --seed 20261026
```

也可用 `evaluate --package … --arm al0|sdk --submission … --output … --fault normal|lost_reply|crash_after_push` 定位单格。SDK 输入必须是已审阅的可信本地 Python；构造子进程**不是沙箱**。未来接入不可信 coding agent 时，需要把构造和类型检查放在不含凭据、无法修改 evaluator/宿主数据的隔离执行环境，再把数据 IR 交给宿主。当前结果不能支持对恶意 Python 提交的安全承诺。

每格保留提交源码、生成绑定、IR、构造与执行诊断、Git 接受记录、运行时 SQLite、事件、原始结果及评分。汇总保存 seed、实际执行顺序、任务配置摘要、工具目录指纹、实现版本及源码摘要。`host.json` 含运行授权，仅用于本地恢复，不应上传；对外归档选择不含授权的报告和校准日志。计时是带进程启动和诊断开销的阶段耗时，不能当作独立语言的运行性能或开发修复时间。

## 证据含义与下一阶段

2026 年 10 月 26 日，本机 Python 3.10.11 / Git 2.50.1.windows.1 完成参考校准：6/6 格成功，三对 IR 完全一致；两种不确定交付均完成对账，所有格 finish 后重放新增事件为 0。完整评分、独立引用回读、费用状态和实现摘要保存在 `models/git_pair_calibration.json`。评测器的 6 项验收与适配器 11 项回归合计 17 项通过（86.266 秒），记录见 `models/git_pair_regression.log`。

参考答案校准只能说明评测链路能执行两组等价程序，并区分规定错误；即使六格全通过，也只有 **1 个开发任务、3 个故障调度、2 个前端**，不是 6 个独立开发样本。没有模型采样、参与者随机分配或真实修复记录，不计算语言效应、显著性、开发成功率或 pass@k。报告的 `causal_language_benefit` 固定为 `not_measured`。

后续按 [实验计划](05-evaluation.md) 扩展到跨模块代码修复及证据绑定任务：先冻结独立开发任务与评分，再分配前端、匹配模型配置/说明/样例与修复预算，保存首次提交、诊断、逐轮修复、费用和最终外部状态。参考答案及校准负例不得混入独立测试任务；用于调试评测器的这些任务也不应作为新语言收益的确认性样本。ContextView 和真实模型成本契约仍按原计划推进。
